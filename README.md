# Подбор учебных материалов · прототип трека 1

Предприниматель описывает задачу своими словами и, по желанию, стадию бизнеса, опыт, формат и сферу. Сервис возвращает пять материалов в порядке пользы. У каждой карточки есть причина выбора, следующий шаг и пометка «Бесплатно» или «Платно». Рядом работает простой метод — подбор по совпадению темы. Режим сравнения показывает оба метода на одном профиле и одном каталоге.

Прототип работает без внешних сервисов, ключей и LLM. В комплекте только вымышленные данные: 23 материала, 12 тестовых профилей и пары совместных записей на шесть курсов. Ссылки ведут на зарезервированный домен `example.org` и не являются адресами платформы.

В корне репозитория лежат папки `backend/`, `frontend/` и `docs/` с кратким планом и UI-китом, `Dockerfile`, файлы `compose.yaml` и `compose.data.yaml`, а также `.github/workflows/`. Команды ниже выполняются из корня, если не указана другая папка.

### Задача фронтендеру

Сделайте так, чтобы человек с пустого экрана мог получить подборку и увидеть эффект истории без устных подсказок.

1. Превратите три примера под формой в действия: «Запустить первую рекламу», «Какой налоговый режим выбрать», «Навести порядок в задачах». Нажатие подставляет запрос и запускает подбор. Пользователь по-прежнему может ввести свою задачу или запросить стартовую подборку с пустой формой.
2. Сделайте видимым пример «Без истории / После пройденного курса». В тестовом демо от первого экрана до сравнения должно быть не больше двух действий. Используйте два запроса к `/api/recommend` с одинаковой пустой задачей и настройками: с пустой историей и с историей вымышленного профиля P11. Покажите, какая рекомендация появилась с историей и какая причина пришла от API. У P12 с недостаточным сигналом проверьте переход к стартовой подборке.
3. В первой карточке выделите причину рекомендации и следующий шаг. Формат, тему и пометки совпадения оставьте на втором плане. Проверьте карточку со ссылкой и карточку с действием без перехода. Используйте существующие токены и компоненты UI-кита.

Начните с [первого экрана](frontend/src/components/IntroPanel.tsx), [формы](frontend/src/components/TaskForm.tsx), [сравнения](frontend/src/components/CompareView.tsx) и [карточки](frontend/src/components/MaterialCard.tsx). Для разработки без Docker выполните `npm ci` и `npm run dev` из `frontend/`, затем откройте `/kit.html` по адресу из вывода Vite. Витрина работает на встроенных примерах. Для полного сценария нужен бэкенд. Можно использовать доступный тестовый стенд через `API_TARGET` или попросить коллегу с Docker проверить сценарий на синтетике. [Снимок контракта API](frontend/src/api/openapi.json).

**Приёмка.** Макет Figma или снимки на 390 и 1120 px, изменения React/CSS и короткая запись сценария. Проверьте клавиатуру и видимость фокуса, холодный старт, выбор примера и сравнение с историей. Приложите результаты `npm test`, `npm run lint` и `npm run build` из `frontend/`.

## Запуск

Комплект собирается и запускается одним способом — через Docker. Нужен Docker с Compose v2, то есть с командой `docker compose`.

```bash
docker compose up --build
```

Интерфейс откроется на <http://localhost:8000>, документация API — на <http://localhost:8000/docs>. Порт опубликован только на `127.0.0.1`, поэтому сервис доступен лишь с этой машины. Остановить его можно клавишами Ctrl+C или командой `docker compose down`.

Контейнер работает без лишних прав и с пределами ресурсов: все capabilities сброшены, корневая файловая система только для чтения, новые привилегии запрещены, 512 МБ памяти без подкачки, 1 CPU, до 128 процессов и потоков, до 1024 открытых файлов. Сервис держит до 63 открытых соединений: при 63 следующий запрос сразу получает 503. После `docker compose stop` или Ctrl+C начатые запросы завершаются в течение 10 с, Docker ждёт 15 с.

Переменные задаются в файле `.env` рядом с `compose.yaml`, образец — [env.example](env.example), список — в разделе «Переменные окружения». Например, строка `APP_PORT=8080` переносит сервис на порт 8080 машины, внутри контейнера он всегда слушает 8000.

Чтобы сервис был доступен другим машинам в доверенной сети, замените адрес `127.0.0.1` в строке `ports` файла `compose.yaml` на `0.0.0.0` или на адрес нужного сетевого интерфейса. Аутентификации в прототипе нет, поэтому в общей сети порт не открывайте. Для доступа из общей сети нужен обратный прокси с таймаутом чтения заголовков: соединение без запроса uvicorn сам не закрывает, и 63 таких соединения занимают все места.

Workflow [.github/workflows/docker-check.yml](.github/workflows/docker-check.yml) запускается при push, pull request, вручную и по расписанию — по понедельникам в 04:37 UTC. По расписанию выполняются все задания: базы уязвимостей pip-audit, npm audit и trivy пополняются и без коммитов. При сборке отдельного репозитория из `app/` папка `.github/` уже на месте. Папку `evaluation/e2e/` и скрипты `evaluation/load_open.py` и `evaluation/load_local.py` положите из рабочей базы в папку `evaluation/` в корне репозитория. Без этих двух скриптов необязательный нагрузочный шаг завершится ошибкой настройки, остальные задания от них не зависят. Workflow выполняет пять заданий, образ собирается один раз — в задании `docker`.

- `backend-tests` ставит зависимости из `backend/requirements-dev.lock` с проверкой хешей и на Python 3.12 выполняет ruff, mypy, тесты бэкенда и проверку покрытия ветвей, см. «Проверки».
- `frontend-tests` запускает `npm --prefix frontend test` и ESLint (`npm --prefix frontend run lint`) на Node.js 26, сверяет копию схемы API `frontend/src/api/openapi.json` со снимком бэкенда, затем `npm run gen:api -- --check` сверяет с ней `frontend/src/api/schema.gen.ts` без записи файла, а `npm run typecheck` — ручные типы через `frontend/src/api/contract.ts`.
- `docker-lint` проверяет Dockerfile правилами BuildKit (`docker build --check`) и hadolint, а workflow — actionlint. Затем выгружает контекст сборки и убеждается, что в нём нет тестов, кешей, документации `docs/`, `node_modules`, `dist`, `.env`, баз SQLite, закрытых и локальных данных.
- `docker` собирает образ с метками OCI: ревизия — SHA коммита, дата — время коммита из `SOURCE_DATE_EPOCH`. Тот же образ задание сканирует trivy и описывает SBOM в формате CycloneDX: сборка падает на уязвимостях HIGH и CRITICAL, для которых есть исправление, отчёты лежат в артефакте `image-scan`. Задание проверяет метки и состав образа: в `/srv/app` лежат только `backend/app`, `backend/data`, `backend/requirements.lock` и `frontend/dist`. Проверяет отсутствие файлов `*.sqlite3` в образе, команду запуска и `HEALTHCHECK`, запускает контейнер и ждёт `/api/ready`. Затем проверяет заголовки ответа (нет `Server`, есть заголовки безопасности), пределы контейнера по `docker inspect`, подбор для P01, ответ 404 `not_found` на `GET /metrics` без `METRICS_ENABLED`, интерфейс в Chromium (`check:ui`, `check:a11y`, `check:wcag`, `check:contrast`, `check:cvd`, `check:display`), Lighthouse CI и статус `healthy`. Lighthouse делает три прогона главной страницы и проверяет медиану по бюджетам из [lighthouserc.yml](lighthouserc.yml), отчёты — в артефакте `lighthouse`. Контейнер должен остановиться быстрее 15 с без SIGKILL. В конце задание запускает контейнер с `compose.data.yaml` на JSON-каталоге из `backend/data` и проверяет, что `/api/health` сообщает источник `file`. При сбое задание выводит журнал контейнера. По расписанию и при ручном запуске задание выполняет и необязательный нагрузочный прогон, см. «Проверки».
- `supply-chain` проверяет блокировки Python через pip-audit, зависимости npm через `npm audit` и подписи реестра. Отчёты и SBOM интерфейса лежат в артефакте `supply-chain`.

Workflow [.github/workflows/mutation.yml](.github/workflows/mutation.yml) раз в неделю и вручную запускает мутационное тестирование mutmut по `backend/app/ranking/`. Порог — 70 % убитых мутантов, отчёт лежит в артефакте `mutation-ranking`.

## Проверки

Проверки повторяют задания CI. Нужны Python 3.12 и Node.js 26.

```bash
# из папки backend
python3.12 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements-dev.lock
.venv/bin/python -m ruff check .
.venv/bin/python -m mypy
.venv/bin/python -m pytest --cov --cov-report=term-missing
.venv/bin/python -m coverage report --include="app/ranking/*" --fail-under=95
```

Настройки проверок лежат в `backend/pyproject.toml`. `ruff check .` применяет правила E, F, B, UP, S, C90, PL и I. Сложность функции не больше 15, ветвлений в функции приложения не больше 12, позиционных аргументов не больше пяти. Исключения заданы для отдельных файлов, причина записана рядом. `ruff format` не обязателен: на 12 ноября 2026 года он переформатировал бы 28 файлов из 52. `mypy` проверяет `app/` в режиме strict. Для `tests/` выключены пять флагов strict: аннотации функций не обязательны, функции без аннотаций можно вызывать, допустимы голые `dict` и `list` и возврат `Any`. Тела тестовых функций mypy всё равно проверяет. `pytest --cov` считает покрытие ветвей `app/` и завершается ошибкой, если оно ниже 85 %. Последняя команда проверяет порог 95 % для `app/ranking/`. Покрытие сравнивается с порогом с точностью до сотых процента, без округления до целого. На 13 ноября 2026 года покрытие ветвей составило 97,07 % для бэкенда и 98,42 % для `app/ranking/` на синтетическом каталоге.

В CI задание `backend-tests` выполняет те же команды отдельными шагами, отчёт `coverage.xml` лежит в артефакте `backend-reports`.

Блокировок две. `requirements-dev.lock` — для проверок локально и в CI: тесты, ruff, mypy, coverage, pip-audit и mutmut. `requirements.lock` — пакеты сервиса для образа, собрана для Linux x86_64 и Python 3.12. После правки `requirements*.txt` пересоберите блокировку командой из её второй строки.

Тесты проверяют порядок выдачи на тестовых профилях, соответствие причин фактическим признакам ранжирования, разбор запроса на наборе фраз, статусы при неполных сведениях, ошибки валидации и HTTP, правила ссылок, демо-режим, загрузчики JSON и SQLite на вымышленных данных и метрики на разметке релевантности `backend/tests/relevance.json`. Отдельные файлы проверяют свойства маршрута и верность объяснений на сетке анкет, заголовки, кеширование, коды запроса и журнал (`test_edge.py`), модуль запуска и меры OWASP API4 и API8, видные в коде (`test_runtime.py`; меры образа и контейнера проверяет задание `docker`), загрузку пар совместных записей (`test_pairs.py`), подбор по истории (`test_history_mode.py`), выключенный по умолчанию каскад правил и похожих курсов (`test_cascade.py`), видимость статей по типу доступа и флагам (`test_visibility.py`), правила микротекстов в причинах, шагах и сообщениях (`test_microcopy.py`) и метрики сервиса (`test_prometheus.py`). `npm run build` в `frontend` проверяет типы TypeScript и собирает интерфейс.

Свойства и контракт API. `test_properties.py` проверяет подбор Hypothesis на сгенерированных профилях: синтетический каталог, фикстуры, синтетический каталог вместе с фикстурами и сгенерированные каталоги, оба метода. Свойства: не больше `limit` материалов, без повторов, без недоступных материалов, без купленных и их копий; тот же вход даёт тот же результат, в том числе при другом `PYTHONHASHSEED`; фразы причин опираются на положительный вклад; порядок по оценке с правилом разнообразия; маршрут только из первой страницы. `test_schemathesis.py` проверяет Schemathesis по `/openapi.json` приложения в процессе, без сервера: нет ответов 5xx, коды, типы и тела ответов описаны в схеме, неверные данные отклоняются, верные принимаются. `test_schema_bounds.py` проверяет границы схемы запроса. `test_openapi_snapshot.py` сверяет `/openapi.json` со снимком `backend/tests/openapi.snapshot.json`. После намеренной правки контракта обновите снимок и копию для интерфейса из папки `backend` командой `python -X utf8 -m tests.test_openapi_snapshot ../frontend/src/api/openapi.json`, затем из корня репозитория выполните `npm --prefix frontend run gen:api`. Команда `npm --prefix frontend run gen:api -- --check` только проверяет, что `frontend/src/api/schema.gen.ts` совпадает со схемой. В CI задание `frontend-tests` сверяет копию схемы со снимком бэкенда, затем выполняет `npm --prefix frontend run gen:api -- --check` и `npm --prefix frontend run typecheck`. Hypothesis работает с `derandomize` и без базы примеров, поэтому прогон повторяется на той же версии Python: CI на 3.12 повторяет локальный прогон на 3.12. Число случайных примеров свойств можно уменьшить переменной `PROPERTY_MAX_EXAMPLES` (по умолчанию 120).

Сквозные сценарии и проверка доступности используют Chromium из Playwright. Запустите сервис командой `docker compose up --build`: в нём собранный интерфейс, тестовый каталог и демо-режим. Из папки, в которой лежит evaluation/e2e/, выполните:

```bash
npm --prefix evaluation/e2e ci
npm --prefix evaluation/e2e run install:browser
npm --prefix evaluation/e2e run check:ui
npm --prefix evaluation/e2e run check:a11y
npm --prefix evaluation/e2e run check:wcag
npm --prefix evaluation/e2e run check:contrast
npm --prefix evaluation/e2e run check:cvd
npm --prefix evaluation/e2e run check:display
npm --prefix frontend test
npm --prefix frontend run typecheck
npm --prefix frontend run lint
```

`check:wcag` проверяет критерии WCAG 2.2, которых нет в axe: страницу без горизонтальной прокрутки на 320 px, цели нажатия 24×24 px, фокус при обходе клавишей Tab, интервалы текста, ошибку поля, печать. `check:contrast` сверяет контраст пар токенов из `frontend/src/styles/tokens.css`, включая пару ролей «рамка уточнения / рамка ошибки». Запущенный сервис для него не нужен. `check:cvd` при работающем сервисе проходит 17 состояний на 390 px и 15 на 1120 px при протанопии, дейтеранопии и тританопии. Скрипт проверяет, что уточнение и ошибку различают видимая строка «Ошибка», форма и светлота рамки, а ссылки-кнопки окрашены в цвет текста и подчёркнуты непрозрачной линией. Видимость строки «Ошибка» проверяется и по стилям, и по пикселям снимка. Прогон занимает около полутора минут, снимки сохраняются в `evaluation/e2e/.results/cvd/`. `check:display` проверяет режим принудительных цветов в тёмной и светлой палитре и увеличение 400 % как окно 320×256 px, около минуты, снимки — в `.results/forced-colors/`; в CI она идёт в задании `docker` вместе с остальными браузерными проверками, а снимки и `display-results.json` попадают в артефакт `browser-checks`. `check:wcag` сохраняет печать сравнения в `print-compare-390.pdf` и `print-compare-1120.pdf`.

`npm --prefix frontend test` — 18 тестов: склонения, форматы строк, типограф, пометки «Совпало» с правилом уровня, правила микротекстов D19 для каждой строки с кириллицей в `src`, кроме витрины. Нужны установленные зависимости `npm ci`. Правила микротекстов лежат отдельным модулем `frontend/tests/microcopy-rules.mjs`. `npm --prefix frontend run typecheck` заодно сверяет ручные типы API со сгенерированными из схемы OpenAPI (`frontend/src/api/contract.ts`).

`npm --prefix frontend run lint` проверяет интерфейс ESLint: правила typescript-eslint strictTypeChecked и stylisticTypeChecked с проверкой типов и правила хуков React. Предупреждения тоже ломают проверку, прогон занимает около 30 секунд. Компилятор интерфейса — TypeScript 6.0: этот же пакет нужен typescript-eslint, который пока не поддерживает TypeScript 7. В tsconfig включены `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` и `noImplicitOverride`.

На Linux для установки системных библиотек Chromium добавьте `-- --with-deps` к команде `install:browser`. По умолчанию проверки обращаются к `http://127.0.0.1:8000`. Другой адрес можно передать после `--`, например `npm --prefix evaluation/e2e run check:ui -- http://127.0.0.1:8080`. `check:contrast` запускается без адреса: первый аргумент после `--` он считает папкой отчёта. Остальные проверки принимают папку отчёта вторым аргументом. npm запускает скрипты из папки `evaluation/e2e`, поэтому относительный путь отсчитывается от неё; надёжнее передать абсолютный. По умолчанию снимки и JSON-отчёты сохраняются в `evaluation/e2e/.results/`. В GitHub Actions они доступны в артефакте `browser-checks` задания `docker`.

Lighthouse CI, аудит зависимостей, сканирование образа и мутационное тестирование идут только в CI, см. описание заданий выше.

По расписанию и при ручном запуске задание `docker` выполняет и необязательный нагрузочный прогон: `evaluation/load_open.py` и `evaluation/load_local.py --slo` против контейнера. Отчёты лежат в артефакте `load`. Неудачный прогон помечает шаг, но задание остаётся зелёным. Код 1 означает, что порог не выполнен, код 2 — ошибку настройки, в том числе отсутствие скриптов, код 3 — исключение в скрипте.

## Маршрут демонстрации

1. Выберите в панели «Демо-режим» профиль P01 и нажмите «Подобрать материалы». Первые три карточки — чек-лист, видео и статья для новичка. У чек-листа в причине названа сфера «кафе и рестораны». Под причиной стоят пометки «Совпало». Ниже — маршрут на первую неделю.
2. Выберите P02 и нажмите «Подобрать материалы». Первым стоит платный курс для растущего бизнеса с краткой пользой и кнопкой перехода. У первых трёх карточек причина цитирует слово задачи: «В задаче вы назвали «эффективность» — материал о теме «Рекламный бюджет и окупаемость»». У платного вебинара нет кнопки перехода: ссылка не передана. Видео помечено «Вы уже открывали».

Пометки «Совпало» есть только у персонального подбора: подбор по теме профиль не учитывает. Выберите P01 и нажмите кнопку ещё раз. Подбор по теме у двух профилей одинаков, персональный различается.

В пятёрке есть курс «Бизнес-план за выходные» из темы «Старт бизнеса» с причиной «Этот курс выбрали 48 из 120 слушателей курса «Старт продвижения за 7 дней» из вашей истории». Затем выберите P12: в его истории пройден курс «Делегирование и процессы», но все пары этого курса ниже порога 10. Подбор по истории не включится, появятся стартовая подборка и вопрос «С чего хотите начать?», как при пустой форме. Со сравнением P11 показывает в колонке подбора по теме стартовую подборку, а в персональной — подбор по истории; экранный диктор слышит итог: «Сравнение готово. Без задачи подбор по теме показывает стартовую подборку, персональный — подбор по истории.»

9. Выполните `docker compose stop` и нажмите «Подобрать материалы». Появится сообщение об ошибке. Выполните `docker compose start` и нажмите «Повторить»: уйдёт тот же запрос, вводить данные заново не нужно.

## Переменные окружения

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `APP_PORT` | Порт на машине пользователя для `docker compose`; внутри контейнера сервис слушает 8000 | `8000` |
| `CATALOG_SOURCE` | `synthetic`, `sqlite` или `file` | `synthetic`, с `compose.data.yaml` — `sqlite` |
| `CATALOG_PATH` | Путь к копии SQLite или к JSON в каноническом формате | пусто, с `compose.data.yaml` — `/data/catalog.sqlite3` |
| `CATALOG_SIGNALS_PATH` | Необязательная база признаков из названий и описаний | пусто, с `compose.data.yaml` — `/data/catalog-signals.sqlite3` |
| `CATALOG_PAIRS_PATH` | Пары совместных записей на курсы для «похожих курсов», JSON; без файла признак отключён | пусто: синтетический каталог берёт пары из комплекта, `sqlite` и `file` — без пар; с `compose.data.yaml` — `/data/course-pairs.json` |
| `PAIRS_MIN_SUPPORT` | Сколько слушателей должны быть записаны на оба курса, чтобы пара учитывалась, от 1 до 1 000 000 | `10` |
| `CATALOG_MAPPING` | Файл соответствия для другой выгрузки, образец — `backend/data/mapping.example.yaml` | пусто |
| `LOCAL_DATA_DIR` | Папка с выгрузкой на машине пользователя, нужна только для `compose.data.yaml` | пусто |
| `DEMO_MODE` | Тестовые профили и режим сравнения: `true`, `false`, `1`, `0`, `yes`, `no`, `on` или `off` | `true` |
| `MAX_TASK_LENGTH` | Предел длины задачи, от 1 до 2000 символов | `300` |
| `METRICS_ENABLED` | Адрес `GET /metrics` со счётчиком запросов и гистограммой длительности в формате Prometheus: `true`, `false`, `1`, `0`, `yes`, `no`, `on` или `off`. Без флага `/metrics` отвечает 404 | `false` |
| `LOG_LEVEL` | Уровень журнала приложения и uvicorn: `debug`, `info`, `warning`, `error` или `critical` | `info` |
| `FRONTEND_DIST` | Папка собранного интерфейса, которую раздаёт бэкенд | `frontend/dist` рядом с папкой `backend`; в образе — `/srv/app/frontend/dist` |

Для `CATALOG_SOURCE`, `DEMO_MODE`, `METRICS_ENABLED` и `LOG_LEVEL` регистр не важен. Недопустимое значение этих переменных, `MAX_TASK_LENGTH` или `PAIRS_MIN_SUPPORT` останавливает запуск до старта сервера: в журнале одна строка вида «Запуск остановлен: LOG_LEVEL должен быть одним из: debug, info, warning, error, critical», код выхода 1.

Переменные `docker compose` берёт из файла `.env` рядом с `compose.yaml`, образец — [env.example](env.example). Журнал пишет код запроса, trace-id из заголовка `traceparent`, метод, путь, статус, число кандидатов и длительность, но не текст задачи. Схема строки описана в начале `backend/app/main.py`. Строки приложения идут в stderr. Строки доступа uvicorn идут в stdout и содержат адрес и порт клиента, метод, путь и статус. Текст задачи не пишет ни один из потоков.

## Своя выгрузка каталога

Выгрузка платформы в SQLite подключается без изменения кода: `CATALOG_SOURCE=sqlite`, путь к базе — `CATALOG_PATH`, необязательная база признаков из названий и описаний — `CATALOG_SIGNALS_PATH`. Статусы публикации, группы тем, рубрики, отрасли, метки уровня и стадии, типы доступа и разбор длительности задаёт файл соответствия. Подписи приватного типа доступа, который скрывает материал, перечислены в `hidden_access_titles`, по умолчанию «Закрытый». Тип самого курса или статьи сверяется с настройками доступа, при расхождении действует более строгий. Образец — `backend/data/mapping.example.yaml`, свой файл указывается в `CATALOG_MAPPING`. База открывается только на чтение. Поле без источника отключает связанный признак, список отключённых признаков и сводка покрытия видны в `GET /api/health`.

Каталог в JSON подключается через `CATALOG_SOURCE=file`, формат файла — как у `backend/data/catalog.synthetic.json`.

Если исходник выдан в формате PostgreSQL `.backup`, сначала подготовьте SQLite штатным импортёром командной копии. В `LOCAL_DATA_DIR` укажите папку с подготовленными файлами. При наличии таблицы `MaterialDetails` приложение читает `PlatformUrl` по паре `MaterialFormat` и `MaterialId`. Оно показывает ссылку только для доступной карточки с адресом HTTP или HTTPS. Для копий без этой таблицы карточки используют действие без перехода. Храните бэкап и подготовленные базы локально.

«Похожие курсы» для своей выгрузки включает файл пар совместных записей в `CATALOG_PAIRS_PATH`. Формат — как у `backend/data/course-pairs.synthetic.json`: объект с полями `version`, `note` и `pairs`, где каждая пара — `{"a", "b", "together", "a_total", "b_total"}`. `a` и `b` — коды курсов в том виде, в каком их выдаёт источник каталога, `together` — число слушателей обоих курсов, `a_total` и `b_total` — число всех слушателей каждого курса. Идентификаторов пользователей в файле нет. Автор прототипа строит такой файл из журнала записей копии своим скриптом, в комплект скрипт не входит. Порог поддержки применяет приложение, поэтому `PAIRS_MIN_SUPPORT` меняется без пересборки файла. Неверный или отсутствующий файл отключает признак, а не загрузку каталога; сводка пар видна в `GET /api/health`.

В Docker папку с данными подключает наложение `compose.data.yaml`. Оно монтирует папку `LOCAL_DATA_DIR` в контейнер как `/data` только на чтение и по умолчанию включает источник `sqlite` с файлами `catalog.sqlite3` и `catalog-signals.sqlite3` из этой папки и необязательным `course-pairs.json` с парами совместных записей; без него «похожие курсы» отключены:

```bash
# в .env: LOCAL_DATA_DIR=<папка с выгрузкой>
docker compose -f compose.yaml -f compose.data.yaml up --build
```

В переменных указываются пути внутри контейнера. Для JSON задайте в `.env` `CATALOG_SOURCE=file` и `CATALOG_PATH=/data/<имя файла>.json`, для своего файла соответствия — `CATALOG_MAPPING=/data/<имя файла>`.

Папка в образ не попадает. В Linux контейнер работает от пользователя с uid 10001, и ему нужны права на вход в папку и чтение файлов. Права можно дать всем или только этому пользователю, например: `setfacl -R -m u:10001:rX <папка>`. Без них каталог не откроется, и `GET /api/health` ответит 503.

## API

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/health` | Состояние, источник и версия каталога, отключённые признаки, сводка покрытия; 503 без каталога |
| `GET /api/ready` | Готовность: 200 `{"status": "ok"}`, если каталог загружен, иначе 503 `catalog_unavailable`. Этот адрес опрашивает `HEALTHCHECK` образа |
| `GET /api/live` | Живость: 200 `{"status": "ok"}`, пока процесс отвечает; каталог не проверяется |
| `GET /api/meta` | Подписи тем, стадий, опыта, форматов и сфер, рабочий предел длины задачи `max_task_length` и признак `demo_mode` |
| `GET /api/profiles` | Тестовые профили, только при включённом `DEMO_MODE` |
| `POST /api/recommend` | Подбор: `method` = `personal` или `baseline` |
| `POST /api/compare` | Оба метода на одном запросе и число изменившихся позиций |
| `GET /metrics` | Только при `METRICS_ENABLED=true`: счётчик `http_server_requests_total` и гистограмма `http_server_request_duration_seconds` в текстовом формате Prometheus 0.0.4. В `/openapi.json` не входит; без флага адрес отвечает 404 `not_found`, это проверяет и CI в задании `docker` |

Пример запроса:

```json
{
  "task": "Хочу начать продвигать свою кофейню, с чего начать?",
  "stage": "start",
  "experience": "none",
  "industry": "horeca",
  "history": [],
  "limit": 5
}
```

Ошибки API приходят в одном виде: `{"error": {"code": "validation_error", "message": "Запрос длиннее 300 символов", "details": [...]}}`. В `details` не больше 10 записей. Коды: 422 — неверный запрос, 413 — тело запроса больше 64 КБ (`payload_too_large`), 404 — неизвестный путь (`not_found`), 405 — неверный метод (`method_not_allowed`, с заголовком `Allow`), 503 — каталог не загружен, 500 — прочие сбои без внутренних подробностей. Статические файлы интерфейса отвечают стандартными кодами HTTP без этого формата, например 416, если диапазон в заголовке `Range` выходит за размер файла.

Пределы запроса: тело до 64 КБ, `task` до `MAX_TASK_LENGTH` символов (по умолчанию 300), `history` до 200 событий, `limit` от 1 до 10. `limit` и `seq` — целые числа JSON: строка `"5"` и `true` получают 422, `8.0` принимается как 8. Полная схема — на `/openapi.json`. Для `task` схема называет жёсткий предел 2000 символов, а рабочий предел `MAX_TASK_LENGTH` сервис сообщает в `GET /api/meta` (`max_task_length`) и проверяет при подборе: задача длиннее рабочего предела получает 422. Схема от настроек не зависит: при любом `MAX_TASK_LENGTH` `/openapi.json`, его снимок и типы интерфейса одинаковы, поэтому клиент берёт предел из `max_task_length`, а не из `maxLength`. Коды ошибок 404, 413, 422 и 503 описаны в схеме моделью `ErrorResponse`: в ответе всегда есть `code`, `message` и `details`, список `details` может быть пустым.

Каждый ответ несёт заголовок `X-Request-Id`. Входящий `X-Request-Id` из 1–64 символов `A–Z`, `a–z`, `0–9`, `.`, `_`, `-` возвращается без изменений, иначе сервер создаёт код из 32 шестнадцатеричных символов. Тот же код стоит в поле `request_id` ответа подбора и в строке журнала. Ответы `POST /api/recommend` и `POST /api/compare` содержат `Server-Timing: rank;dur=…, total;dur=…` в миллисекундах. `GET /api/meta` и `GET /api/profiles` отдают `ETag` с `Cache-Control: no-cache` и отвечают 304 на совпавший `If-None-Match`. Остальные ответы API и все ошибки отдаются с `Cache-Control: no-store`. Ответы от 1 КБ сжимаются gzip, если клиент его принимает. Файлы из `assets/` кешируются на год с `immutable`, HTML — с `no-cache`, шрифты — на час.

Заголовки безопасности стоят на всех ответах приложения: `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy` и CSP без `'unsafe-inline'`. На страницах документации API CSP нет. CORS не включён. Собственные ответы uvicorn — 503 сверх предела соединений и 400 на испорченный HTTP — идут без этих заголовков.

С `METRICS_ENABLED=true` адрес `/metrics` отдаёт данные для Prometheus: число запросов и их длительность в секундах с границами корзин от 0,005 до 10 с. Меток три: `http_route` — шаблон маршрута, например `/api/recommend`, `http_request_method` и `http_response_status_code`. Со сборкой интерфейса его файлы и ответы 404 вне `/api` собраны под шаблоном `/{path:path}`. Запросы без маршрута собраны под `none`: это неизвестные адреса `/api/…`, а без сборки и прочие неизвестные адреса. Неизвестные методы собраны под `_OTHER`, поэтому ни путь, ни метод запроса не создают новых значений меток. Опросы самого `/metrics` не учитываются. Значения хранятся в памяти процесса и обнуляются при перезапуске. Аутентификации у адреса нет, как и у API: при публичном развёртывании флаг не включайте или закройте `/metrics` на обратном прокси.

## Как устроен подбор

- **Подбор по теме** находит темы в задаче по словарю основ и сортирует материалы темы по популярности.
- **Персональный подбор** складывает вклады признаков: тема, признак из текста материала, стадия, уровень, сфера, формат, длительность для новичка, продолжение по редакционным связям и история. Пройденное и просмотренное опускается, начатый курс поднимается. В пятёрке не больше трёх материалов одного формата, если другой формат близок по оценке.
- **Причина** собирается из признаков с наибольшим вкладом, две–три фразы. Если слова задачи нашли признак материала, причина их цитирует: «В задаче вы назвали «CRM» — материал о теме «Работа с CRM и клиентской базой»». Цитата не вытесняет других фраз: если с ней в причину до 180 символов вошло бы меньше фраз, остаётся фраза без цитаты. Тема, выбранная в уточнении, которой нет в задаче, называется так: «Вы выбрали тему «Старт бизнеса»». Пометки истории показываются бейджами, под причиной — пометки «Совпало».
- **Неполные сведения.** Пустая задача даёт стартовую подборку, а если у курса из истории есть пара совместных записей от порога с курсом, которого в истории нет, — подбор по истории с выбором темы. Задача на две темы даёт уточнение. Тема вне каталога даёт честное сообщение и выбор темы.
- **Похожие курсы.** При пустой задаче и такой паре персональный подбор опирается на историю. Он поднимает материалы тех же тем и курсы, на которые записывались слушатели курсов из истории, в том числе курсы других тем. Причина называет числа: «Этот курс выбрали 48 из 120 слушателей курса «Старт продвижения за 7 дней» из вашей истории». У курса другой темы эта причина есть всегда. Пара учитывается, если на оба курса записаны не меньше `PAIRS_MIN_SUPPORT` слушателей, а у курса истории их не меньше 10. Подбор по теме историю не учитывает.
- **Понятие без темы.** Если задача называет понятие, но не тему, например «Какую CRM выбрать», персональный подбор берёт материалы с этим понятием из любых тем. Если таких нет, показывается честное сообщение. Подбор по теме понятий не различает и в этом случае предлагает стартовую подборку.
- **Узкий запрос.** Для словарных запросов о лицензировании, продаже алкоголя, сертификации и визах, в которых нет отдельного понятия вроде CRM, сервис ищет все распознанные признаки в одном названии. Персональный метод ищет по всему каталогу доступных материалов, подбор по теме ограничивается распознанными темами. Поэтому совпадение только в описании материала может быть пропущено. Если подходящих названий нет, сервис сообщает об этом и предлагает выбрать тему. Ручной выбор включает обычный подбор по теме.

Веса — гипотеза первого прототипа. Тесты проверяют порядок на профилях, а не сами числа.

### Вопросы анкеты и признаки ранжирования

Все поля необязательны. Ответ добавляет вклад в оценку материала, веса заданы в `backend/app/ranking/personal.py`. Подсказка из текста задачи действует, только если на соответствующий вопрос нет ответа. Пропущенный вопрос материал не штрафует: признак берётся из текста задачи или не учитывается. Материал без разметки стадии, уровня или сферы по этому признаку нейтрален.

| Вопрос | Признак ранжирования | Что без ответа |
| --- | --- | --- |
| «Что вы хотите сделать?», текст задачи | Тема по словарю отбирает кандидатов и даёт +3,0. Понятие вроде «CRM» или «юнит-экономика» даёт +2,0, если оно есть в названии материала, и +1,0, если только в описании; учитывается одно понятие. Если темы в задаче нет, понятие само отбирает материалы из любых тем. Из текста берутся и подсказки для остальных вопросов, см. строки ниже. Причина цитирует слова задачи, по которым найдено понятие: «В задаче вы назвали «CRM» — материал о теме «Работа с CRM и клиентской базой»» | Стартовая подборка: самый популярный вводный бесплатный материал по каждой теме и вопрос «С чего хотите начать?». Уточнения на неё не влияют, пройденные и купленные материалы в неё не попадают. Исключение — история, в которой у курса каталога есть пара совместных записей от порога с курсом вне истории: тогда подбор идёт по истории, см. строку «История» |
| Стадия бизнеса: «Только планирую», «Недавно начал(а)», «Работаю и расту» | +2,0, если стадия есть в разметке материала. При «Только планирую» и «Недавно начал(а)» выдача без уточнения темы может получить маршрут на первую неделю: до трёх материалов первой страницы выдачи, связанных редакционными ссылками от первой карточки. Если у первой карточки нет такой связи, маршрута нет | Подсказка из текста: «с чего начать», «с нуля», «впервые» означают старт, «масштабировать», «расширить» означают рост. Совпадение со стадией материала даёт +1,0. Подсказка старта действует на маршрут так же, как ответ «Недавно начал(а)». Без подсказки вклад 0 |
| Опыт в теме: «Новичок», «Кое-что знаю», «Уверенно разбираюсь» | Опыт по порядку сопоставляется с уровнем материала: «Для начинающих», «Практика», «Продвинутый». +2,0 за тот же уровень, +1,0 за соседний. Новичку +0,5 за материал до 30 минут, если формат не выбран и не назван в тексте | Подсказка из текста: «новичок», «с нуля», «основы» означают уровень для начинающих, «продвинутый», «углублённо» означают продвинутый. +1,0 только за тот же уровень; подсказка уровня для начинающих даёт и +0,5 за короткий материал. Без подсказки вклад 0 |
| Нужный формат: «Быстрый ответ», «Шаблон», «Курс или вебинар» | +1,5 за формат из группы: статья, чек-лист, видео; шаблон, документ; курс, вебинар, подкаст | Подсказка из текста: «быстро», «кратко», «чек-лист», «памятка»; «шаблон», «образец», «бланк»; «курс», «обучение», «вебинар». Совпадение даёт +1,0, без подсказки вклад 0 |
| Сфера бизнеса: список, по умолчанию «Не указана» | +1,0, если сфера есть у материала | Синоним из текста даёт тот же +1,0: «кофейня» и «ресторан» означают кафе и рестораны, «магазин» означает розничную торговлю, «интернет-магазин» и «маркетплейс» означают интернет-торговлю. Без синонима вклад 0 |
| История: в форме вопроса нет, события приходят из тестового профиля или от кнопки «Отметить изученным» | Начатый материал +2,0 и пометка «В процессе», просмотренный −1,5 и «Вы уже открывали», пройденный −4,0 и «Пройдено», купленный не показывается. Материал из редакционных связей последнего события, которого в истории нет, получает +1,5 как продолжение. Пилот «похожие курсы»: при пустой задаче без выбранной темы, если у курса каталога в истории, доступного или нет, есть пара совместных записей от порога с допустимым курсом вне истории, кандидаты — материалы тем истории и курсы, связанные парой с курсом истории. Без такой пары остаётся стартовая подборка, даже если в истории есть начатый материал. Тема истории даёт +0,1. Связанный курс получает 3,0 × долю слушателей курса истории, записанных и на него; доли по нескольким курсам истории складываются, вклад не больше 3,0. Учитываются пары с поддержкой не ниже `PAIRS_MIN_SUPPORT`, по умолчанию 10. Курс истории учитывается, если у него не меньше 10 слушателей: иначе фраза «N из M» не говорила бы о доле. Пары берутся из `CATALOG_PAIRS_PATH`; если переменная пуста, синтетический каталог берёт пары из комплекта, а другие источники остаются без пар. Ответы анкеты действуют как обычно; статус `weak` с вопросом «Уточните тему», маршрута нет | Вклады истории равны 0 |
| Тема в уточнении: баннер «Уточните тему», когда тема задачи неоднозначна или подбор идёт по истории, и выбор темы при пустой задаче или пустой выдаче | Выбранная тема заменяет распознанные: кандидаты только из неё, +3,0, уточнение больше не задаётся. Форма не очищается. При пустой задаче и курсе в истории курсы выбранной темы получают и вклад пар совместных записей. Если задача тему не называет, причина говорит о выборе: «Вы выбрали тему «…»» | Учитываются темы из текста. Если их несколько, выдача включает материалы всех и показывает баннер. При подборе по истории учитываются темы истории и связанные курсы. «Оставить как есть» скрывает баннер, выдача не меняется |

## Ограничения

- Демонстрация идёт на синтетическом каталоге. Прогон на копии реальной выгрузки выполняется только локально у автора: копия не входит в комплект.
- Влияние на конверсию в покупку и активные дни не измерено. Для этого нужен онлайн-эксперимент с телеметрией.
- Аутентификации нет: прототип рассчитан на локальный запуск.
