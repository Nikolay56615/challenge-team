# Трек 1. Рекомендации материалов

Опирайся на R1–R3 из [карты проекта](../PROJECT.md) и [условие кейса](../materials/case.md). Ниже варианты прототипа и проверок. Подтверждённый выбор появляется в [CURRENT.md](../CURRENT.md).

## Вход и результат

Вход — каталог, текущая задача и доступная часть профиля. Структура профиля может включать стадию, сферу, опыт и историю просмотров. Считай отсутствие каждого поля отдельным состоянием. Выход — ранжированный список из каталога с короткой причиной и следующим действием по каждому элементу.

Проверь фактическое покрытие каталога. По каждой значимой теме оцени, есть ли вводный, прикладной и углублённый материал, какие уровни и форматы различимы и какие ссылки разрешены. Правила подбора должны опираться на поля, которые реально можно получить. [Контракт данных](data.md).

## Первый сквозной сценарий

1. Новый предприниматель указывает задачу «начать продвижение».
2. Система предлагает полезные материалы даже без истории. Одним необязательным вопросом можно уточнить стадию или нужный формат.
3. Ответ перечисляет несколько элементов, для каждого объясняет совпадение и указывает действие. Пример для синтетического материала M01 — «Чек-лист подходит для первого запуска. Начни с выбора аудитории и цели».
4. Тот же профиль проходит через бейзлайн по теме. Сохрани обе выдачи, порядок и объяснения.
5. Проверь неполный профиль, неизвестную тему и доступную историю. При слабом покрытии покажи уточнение, общую подборку или маршрут из существующих материалов.

## Варианты ранжирования

| Вариант | Когда применять | Что проверить |
| --- | --- | --- |
| Бейзлайн по теме | Для сопоставимого исходного уровня | Нормализацию темы, стабильный порядок при равном совпадении и общий запасной режим |
| Правила с признаками профиля | В каталоге есть уровни, стадии, форматы, история опциональна | Отдельный вклад каждого признака, нейтральность пропусков, причины результата и устойчивость к ложной классификации |
| Семантический поиск или гибрид | Пользователи часто перефразируют задачу, а по ключевым словам теряются кандидаты | Сравнение на одинаковых запросах, задержку, приватность, стоимость и объяснимость. Включать при наблюдаемой пользе |
| Модель на событиях | Доступен достаточно полный журнал с понятными событиями и временным порядком | Разделение по времени, утечки через будущие действия, популярность и полезность для холодного старта |

Сначала отфильтруй недоступные или непригодные элементы. Затем собери кандидатов, оцени пригодность и разреши равенства стабильным правилом. Для простой проверки можно считать баллы по теме, стадии, уровню и формату. Конкретные веса — гипотеза, которую нужно проверить на разных профилях. При отсутствии истории опирайся на каталог и запрос. При наличии истории учитывай поведение, если оно относится к текущей задаче, и проверь обработку уже просмотренного контента.

## Пример сравнения

Синтетический каталог содержит чек-лист для запуска (M01), продвинутый курс для растущего бизнеса (M02) и шаблон для действующего малого бизнеса (M03). У всех одна тема. Для начинающего P01 подходит M01, для опытного P02 с задачей системного продвижения — M02 или M03 в зависимости от ожидаемого формата.

| Случай | Ожидание от проверяемой версии |
| --- | --- |
| P01, запрос о первом запуске | M01 выше M02, причина связана со стадией и форматом |
| P02, просит системный курс | M02 выше вводного чек-листа. Если материал платный, показать только допустимую карточку |
| Пользователь без истории и анкеты | Полезный результат по доступному запросу либо общая подборка |
| Незнакомая тема | Честное описание пробела, уместный вопрос или ближайший маршрут |
| Равные баллы | Стабильный порядок и понятные причины при повторном прогоне |

На малой выборке приведи сами результаты и ошибки. При наличии разметки добавь `hit@k` для попадания подходящего материала и `NDCG@k` для порядка с градациями полезности. Обоснуй k длиной интерфейса. Сравнение и продуктовый эксперимент описаны в [оценке](evaluation.md). Официальные справки по архитектуре и метрикам — в [каталоге](../SOURCE_MANIFEST.md).

Для браузерной демонстрации используй [руководство по веб-интерфейсу](web-demo.md). После первого сквозного прогона примени [план инженерной проверки](recommender-reliability.md). Он покрывает доступ к данным, сбои, параллельные запросы и производительность. Эти проверки дополняют сценарии и критерии из условия.
