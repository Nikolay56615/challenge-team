# Сборка, демонстрация и защита

Это инструкция к будущей сдаче. Подготовку локального комплекта начинает `/prepare-submission` по явному запросу пользователя. Выбранный трек, требования допуска и веса см. в [условии](../materials/case.md). Статус разработки — в [CURRENT.md](../CURRENT.md).

## Что должно быть в комплекте

| Файл или материал | Что подтвердить |
| --- | --- |
| Исходный код | Включён только нужный код. Из него запускается выбранный трек |
| README для запуска | Назначение, схема компонентов, одна проверенная команда запуска через Docker, переменные, порты, зависимости, входы, шаги проверяющего, ограничения |
| Dockerfile, compose.yaml, .dockerignore | Воспроизводимый запуск и явный состав контекста сборки |
| Файл зависимостей | Версии зафиксированы в выбранном формате |
| env.example | Имена параметров, безопасные примеры или пустые значения. Отдельно описано, как получить и передать необходимые ключи |
| Презентация в PDF | Порядок проверки на первом слайде, затем проблема, пользователь, архитектура, сценарий, примеры, ограничения и развитие |
| Репозиторий или ZIP | Состав соответствует выбранному формату. Доступ и загрузка выполняются по отдельному поручению пользователя |

Для трека 2 в README нужен порядок подключения тестового токена. При использовании внешней модели укажи сервис, модель, имя переменной и способ подключения. При наличии развёрнутого интерфейса в презентации указывают ссылку, а для развёрнутого бота обеспечивают работу в окно проверки.

## Пример оформления инструкции запуска

Будущий README начинается с назначения и одного главного маршрута. Укажи требуемую версию Docker/Compose, какие входы нужны и где взять разрешённый демонстрационный набор. Для выбранного приложения проверь, какой способ передачи переменных использует Compose. Если проект после реализации поддержит команду `docker compose up --build`, внеси её только после фактического прогона. Добавь ожидаемый признак готовности, затем конкретные шаги пользователя и наблюдаемый результат. [Команды и переменные Docker Compose](../SOURCE_MANIFEST.md).

Пример проверочного сценария для трека 1 — ввести задачу «первое продвижение», получить подборку, открыть причину первого результата, затем показать изменение выдачи для более опытного профиля. Для трека 2 — задать вопрос с источником, включить напоминание, показать тестовую доставку, изменить частоту и отключить.

## Проверка перед передачей

1. Собери комплект из разрешённого списка файлов. Личные данные, `Personal/`, сырые выгрузки, локальные конфигурации, секреты, старые копии и закрытые материалы исключи до чтения и упаковки.
2. Проверь фактический архив или дерево. Проверь пути, метаданные, содержимое документов, вложенные контейнеры, ссылки и отсутствие прямых зависимостей на локальное окружение автора.
3. Запусти из чистой копии по инструкции. Пройди главный маршрут, сверяйся с [матрицей](evaluation.md). Зафиксируй отличие тестового транспорта от реальной интеграции, если оно есть.
4. Вычитай русский текст README, презентации и речи по [руководству по редактуре](russian-style.md). Сверь числа и выводы с протоколом, затем проверь презентацию визуально и открой разрешённые ссылки в режиме проверяющего. Убедись, что на первом слайде понятен порядок проверки.
5. Опиши известные ограничения, результат прогона и шаги, требующие участия пользователя. Для приватного доступа и публикации понадобятся подтверждённые реквизиты вне обезличенной рабочей базы.

## Структура демонстрации

- **Проблема и персона.** Например, начинающий предприниматель ищет конкретный первый шаг.
- **Результат.** Покажи полный путь от запроса до полезного результата и одно пограничное поведение.
- **Архитектура.** Покажи, где появляются данные, как проходит запрос и где применяется ограничение на доступ.
- **Проверка.** Назови один воспроизводимый прогон и что он подтверждает. Отдельно покажи план онлайн-измерений.
- **Границы и развитие.** Объясни, какие данные или проверки нужны для следующей версии. Подготовь ответы о выборе подхода, качестве данных, воспроизводимости и приватности.
