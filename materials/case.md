# Кейс 2. Образовательная платформа для предпринимателей

Обезличенная текстовая версия предоставленного кейса. Ниже зафиксированы требования к прототипу и условия его оценки.

## Цель и бизнес-контекст

Нужно разработать работающий прототип по одному из двух треков. Общая бизнес-цель — повысить среднюю конверсию в покупку образовательных продуктов. Дополнительная продуктовая цель — увеличить число дней, в которые пользователь заходит на платформу.

Платформа предлагает бесплатные и платные материалы для малого и микробизнеса, начинающих предпринимателей и соло-фаундеров. Темы включают запуск бизнеса, бухгалтерский учёт, маркетинг, продажи и повседневную организацию работы. По одной теме пользователю может понадобиться быстрый ответ для решения сегодня, готовый шаблон или полноценный курс. При подборе важны стадия бизнеса, опыт и действие, которое человек готов совершить.

## Целевая аудитория

| Пользователь | Типичная ситуация | Нужная помощь |
| --- | --- | --- |
| Начинающий предприниматель | Планирует открыть дело и ищет первый шаг | Вводный материал и последовательность действий |
| Владелец малого или микробизнеса | Решает конкретную задачу по учёту, маркетингу или продажам | Краткая инструкция, готовый инструмент или ответ на вопрос |
| Соло-фаундер или предприниматель, развивающий бизнес | Хочет освоить новую область и улучшить процесс | Подборка по уровню и пояснение, когда нужен углублённый курс |

Пользователь может не знать профессиональных терминов и не захотеть заполнять длинную анкету. Решение должно помогать и при неполных сведениях.

## Трек 1. Персональные рекомендации образовательных материалов

1. Изучить каталог и определить, какие поля помогают подобрать материал под задачу пользователя.
2. Подбирать и ранжировать материалы с учётом стадии и сферы бизнеса, текущей задачи, опыта и истории просмотров, если она есть.
3. Предусмотреть холодный старт с полезной подборкой для нового пользователя и коротким необязательным онбордингом.
4. Объяснять каждую рекомендацию и предлагать следующий шаг.
5. Сравнить решение с простым базовым методом, например подбором по совпадению темы, на самостоятельно составленных тестовых профилях.
6. Предложить способ измерить влияние рекомендаций на конверсию после внедрения.

## Трек 2. ИИ-помощник для предпринимателей в Telegram

1. Отвечать на вопросы по базе знаний платформы.
2. Уточнять неоднозначные вопросы и прямо сообщать, когда в базе нет ответа.
3. Собирать в диалоге сведения о бизнесе пользователя и учитывать их в ответах.
4. Рекомендовать подходящие бесплатные и платные материалы по ходу консультации.
5. Поддерживать разовые и повторяющиеся напоминания об обучении и деловых событиях, например о сроке уплаты налога по режиму пользователя. Дать возможность менять частоту и отключать напоминания. Интервалы выбирает команда.
6. Объяснить, как бот возвращает пользователей на платформу, и предложить способ измерить эффект после внедрения.

## Пространство решений

Язык, фреймворки и стек свободны. Допустимы локальные модели и внешние LLM или API. В треке 1 можно использовать правила, ML-модели, LLM и их сочетания. В треке 2 способ поиска по базе и формат диалога свободны. Для проверки допустимы вымышленные пользователи, диалоги и события. Дополнительные функции допустимы, если помогают пользователю и решают задачи бизнеса.

## Ограничения

1. Предоставленные данные используются только для выполнения кейса. Исходные выгрузки и их копии запрещено публиковать в открытых репозиториях и общедоступных хранилищах или передавать третьим лицам.
2. Сложные интеграции с банковскими и государственными сервисами не требуются.
3. Интерфейс должен быть простым и понятным.
4. Рассылки и уведомления не должны быть навязчивыми. Всплывающие окна должны иметь понятную цель.
5. Подробное содержание платных материалов закрыто. Для подходящего материала следует кратко объяснить пользу и предложить переход на его страницу или страницу покупки по предоставленной ссылке.
6. Во внешние API передаются только необходимые фрагменты. Персональные данные и закрытые материалы, не предназначенные для сторонних сервисов, исключаются. Для демонстрации используются тестовые профили.

## Данные

В условии описана выгрузка с образовательными материалами, их характеристиками и взаимодействиями пользователей с платформой. Выгрузка и описание схемы в этот проект не включены. Названия полей, объём и форматы фактических данных предстоит подтвердить по разрешённой копии.

## Примеры сценариев проверки

### Трек 1

1. Новый пользователь указывает текущую задачу, например продвижение бизнеса. Система подбирает стартовые материалы из каталога и объясняет их порядок.
2. Если история действий есть, система может использовать зафиксированные в журнале взаимодействия для улучшения подбора. При холодном старте или отсутствии журнала система даёт рекомендации, которые могут повысить частоту взаимодействия с платформой. Допустимы синтетические события.
3. При нехватке сведений или отсутствии точного совпадения система задаёт уточняющий вопрос, даёт более общую подборку или предлагает маршрут изучения по имеющимся материалам.

### Трек 2

1. Пользователь задаёт вопрос по теме из базы знаний. Бот отвечает на основе базы и предлагает подходящий материал, если он есть.
2. Пользователь просит напомнить об обучении или деловом событии. Бот уточняет данные, подтверждает разовое или повторяющееся напоминание и отправляет сообщение в назначенное время. Пользователь может изменить частоту повторений или отключить их.
3. Если вопрос неоднозначен или ответа в базе нет, бот уточняет запрос либо сообщает, какой информации не хватает.

## Формат сдачи

Условие предусматривает два варианта сдачи через площадку проверки:

- Презентация в PDF со ссылкой на репозиторий на первом слайде.
- ZIP-архив с исходным кодом, документацией и презентацией в PDF.

На первом слайде нужны порядок проверки и, при сдаче через репозиторий, ссылка на него. Если интерфейс развёрнут, нужна ссылка на него. Для приватного репозитория проверяющим нужен доступ. Реквизиты площадки и аккаунта проверяющих исключены из этой версии. Далее в презентации описываются проблема, пользователь, архитектура, сценарий консультации, примеры работы, ограничения и идеи развития.

Состав репозитория или архива:

- Исходный код выбранного трека.
- `README.md` с назначением, архитектурой, одной командой запуска через Docker, переменными окружения, портами, зависимостями, описанием входных данных, пошаговой проверкой и известными ограничениями.
- При использовании внешнего API в README указываются сервис, модель, переменная для ключа, способ получения и подключения ключа. Для трека 2 нужен порядок подключения токена Telegram-бота.
- `Dockerfile`, `compose.yaml` и `.dockerignore` для воспроизводимого запуска.
- Файл зависимостей с зафиксированными версиями, например `requirements.txt`.
- `env.example` без рабочих ключей и паролей. Рабочие ключи и токены не прикладываются к сдаче.

Развёрнутый Telegram-бот должен работать во время экспертной проверки. При локальной проверке он должен запускаться по README через Docker и принимать токен и необходимые API-ключи через переменные окружения.

## Допуск и оценка

Работа получает 0 баллов и дальше не оценивается, если отсутствуют исходный код, презентация или необходимые инструкции по запуску, либо если решение не запускается по инструкции или основной сценарий нельзя пройти до результата. Недочёты документации и частичные сбои, при которых основной сценарий проходим, учитываются в соответствующих критериях.

Шкала для каждого критерия:

| Баллы | Описание |
| --- | --- |
| 0 | Функциональность отсутствует или результат не представлен |
| 1 | Есть отдельные элементы, критерий практически не выполнен |
| 2 | Критерий выполнен в небольшой степени, есть существенные пробелы |
| 3 | Критерий выполнен частично, есть заметные недочёты |
| 4 | Критерий в основном выполнен, недочёты несущественны |
| 5 | Критерий выполнен полно и качественно |

Веса и шкала одинаковы для обоих треков. Эксперты учитывают требования и сценарии выбранного трека. Обязательные только для другого трека функции не дают дополнительных баллов.
