# План трека 1

Сервис подбирает учебные материалы под задачу предпринимателя и объясняет каждую рекомендацию. Для проверки сравниваем персональный подбор с подбором по теме на одном запросе и каталоге. [Условие трека](../materials/case.md#трек-1-персональные-рекомендации-образовательных-материалов)

## 2. Данные

### 2.1 Источники каталога

По умолчанию загружаются 23 тестовых материала и 10 вымышленных профилей. Для отдельной проверки подключается разрешённая SQLite-копия на чтение. Пути и команды описаны в [инструкции по данным](data.md).

### 2.2 Поля материала

Для подбора используются тема, формат, доступность, стадия, уровень, сфера, длительность, популярность и связь с продолжением. Пропуски уменьшают число признаков, которыми можно обосновать выбор. Платность и допустимая ссылка нужны для отображения карточки. [Модель каталога](../backend/app/catalog/models.py)

### 2.3 Темы и сопоставление

Справочники переводят признаки выгрузки в единые коды. Каталог может использовать нейтральные метки из названий и описаний. Сводка покрытия доступна в `/api/health`. [Словари](../backend/app/vocab.py) · [Пример сопоставления](../backend/data/mapping.example.yaml)

### 2.4 История

Для демо используются вымышленные просмотры и завершения. В локальной выгрузке доступны взаимодействия с курсами и относительный порядок событий. Флаг `IsPaid` встречается в 22 из 10 050 записей, а дата покупки пуста во всех. Метрику покупок рассчитываем по подтверждённым оплатам. [Описание выгрузки](data-description.md)

### 2.5–2.8 Тестовые данные и загрузка

Синтетический каталог, тестовые профили и варианты загрузки описаны в [README](../README.md). P01 и P02 показывают, как профиль меняет порядок при близкой теме. P04 и P05 проверяют пустую выдачу и уточнение. [Тестовые профили](../backend/data/profiles.synthetic.json)

## 3. Подбор и проверка качества

- **3.1 Бейзлайн.** Отбирает по совпадению темы, затем сортирует по популярности.
- **3.2–3.3 Персональный метод.** Учитывает задачу, профиль, формат и историю. Правила позволяют объяснить порядок и отдельно проверить вклад признаков. [Ранжирование](../backend/app/ranking/personal.py)
- **3.4–3.5 Холодный старт и слабое совпадение.** Пустая форма даёт стартовую подборку. Для неоднозначной задачи уточняем тему. Если материалов нет, показываем пробел и предлагаем продолжить подбор.
- **3.6 Карточка.** Показывает причину и следующий шаг. Переход доступен при наличии разрешённой ссылки. «Отметить изученным» обновляет историю сеанса.
- **3.7 Оценка.** На восьми синтетических профилях с определённой метрикой средний NDCG@5 составил 0,92 у персонального метода и 0,72 у подбора по теме. Результаты локальной офлайн-оценки курсов приведены отдельно. [Протокол первого прогона](../evaluation/track1-first-run.md) · [Офлайн-оценка](../evaluation/track1-offline-courses.md)

## 4. Архитектура, API и запуск

React и TypeScript собираются Vite. FastAPI обслуживает API и отдаёт собранный интерфейс. Ранжирование отделено от HTTP-слоя. Docker собирает фронтенд и бэкенд в одном образе. [Dockerfile](../Dockerfile)

- `GET /api/health` показывает готовность и источник каталога.
- `GET /api/meta` отдаёт справочники и возможности источника.
- `GET /api/profiles` отдаёт тестовые профили в демо-режиме.
- `POST /api/recommend` принимает задачу, профиль и историю сеанса.
- `POST /api/compare` возвращает выдачу обоих методов на одном входе.

Контракт запускается локально на `http://localhost:8000/docs`. Команды Docker, настройка переменных и запуск для разработки описаны в [README](../README.md). Локальные данные монтируются только на чтение.

## 5. Спецификация интерфейса

Форма принимает задачу, необязательные уточнения и историю сеанса. Сверяйте форму, карточки, режим сравнения и состояния загрузки, пустой выдачи, уточнения и ошибки по [макету](../design/track1/mockup.html) и [UI-киту](../design/ui-kit.md). Браузерная проверка проводится на 390 и 1120 px и с клавиатурой.

### 5.7 Тексты интерфейса

Форма спрашивает «Что вы хотите сделать?». В карточке видны «Почему подходит» и «Следующий шаг». При неоднозначном запросе показывается «Уточните тему». После ошибки пользователь может повторить запрос с сохранённым вводом.

## 6. Порядок работы команды

1. Запустите проект из чистого клона и пройдите P01 и P02.
2. Сверьте карточки и состояния с UI-китом. Если меняется дизайн, приложите снимки до и после.
3. При изменении ранжирования проверьте оба метода на тех же профилях и запишите ожидаемое отличие.
4. Сверьте презентацию с фактическим запуском и протоколом. [Чек-лист](review.md) · [План слайдов](presentation.md)

## 7. Проверки

### 7.1 Запуск и демонстрация

Пройдите сценарии из [чек-листа](review.md). Первоначальная Docker-сборка и проверки API завершились успешно локально и в [GitHub Actions](https://github.com/Nikolay56615/challenge-team/actions/runs/42805063943).

### 7.2 Безопасность и нагрузка

Проверьте, что API и логи не раскрывают закрытые поля, а локальные базы отсутствуют в образе. Для замера укажите каталог, число клиентов, p95 и ошибки. Предварительные замеры без Docker и методика описаны в [протоколе](../evaluation/track1-first-run.md).

### 7.3 Измерение эффекта

После внедрения случайно распределить пользователей между текущим способом выбора и персональной витриной. Основная метрика — доля пользователей с подтверждённой покупкой в течение 30 дней, дополнительная — число активных дней. Для оценки нужны события назначения группы, показа рекомендаций, перехода, визита и подтверждённой оплаты.
